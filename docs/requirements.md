# Требования безопасности

[Паспорт](../PROJECT.md) · [Модель угроз](threat-model.md) · [Решения](design-decisions.md)

Критерий приёмки задаёт ситуацию и наблюдаемый результат. «Статус» — есть ли уже реализация и автоматический тест; выполненный тест — это проверка, а не только план.

<a id="sr-01"></a>
### SR-01. Субъект запроса — только из действующей серверной сессии

**Требование.** Любой endpoint, кроме входа и `/health`, выполняется от имени пользователя, определённого по действующей сессии: токен известен серверу, не отозван, не истёк, учётная запись активна. Идентификатор пользователя и роль из тела или параметров запроса не принимаются.  
**Защитное свойство.** Подлинность субъекта: без действующего токена нельзя действовать от имени другого пользователя.  
**Критерий приёмки.** Запрос к `/me` или `/students` без заголовка `Authorization`, с произвольной строкой токена, с истёкшим токеном или токеном деактивированного пользователя → `401` без данных. Тело входа или создания пользователя с полем `role: "admin"` → `422`, роль не меняется.  
**Связи:** [T-01](threat-model.md#t-01) → [D-01](design-decisions.md#d-01). **Статус:** реализовано, тесты `tests/test_auth_api.py`.

<a id="sr-02"></a>
### SR-02. Выход немедленно отзывает сессию; срок жизни сессии ограничен

**Требование.** После `POST /auth/logout` токен перестаёт действовать сразу, на всех экземплярах сервера. Сессия действует не дольше `SESSION_TTL_HOURS` (по умолчанию 12 ч).  
**Защитное свойство.** Украденный токен нельзя использовать после выхода владельца; окно использования ограничено.  
**Критерий приёмки.** Вход → `/me` = `200` → logout = `204` → тот же токен на `/me` = `401`. Сессия с `expires_at` в прошлом → `401`.  
**Связи:** [T-01](threat-model.md#t-01) → [D-01](design-decisions.md#d-01). **Статус:** реализовано, тесты `tests/test_auth_api.py`.

<a id="sr-03"></a>
### SR-03. Секреты не хранятся и не возвращаются в открытом виде

**Требование.** Пароли хранятся только как argon2id-хеш; токены сессий — только как SHA-256. Ответы API, включая ошибки 422 и 500, не содержат паролей, хешей, токенов (кроме выдачи токена при входе), SQL и трассировок. Строка подключения к БД и пароль администратора берутся из окружения, а не из репозитория.  
**Защитное свойство.** Утечка БД или логов не даёт готовых токенов и паролей.  
**Критерий приёмки.** После входа в таблице `sessions` нет значения выданного токена, в `users` нет пароля в открытом виде; ответ 422 на тело с неверным значением не содержит этого значения; ответ на внутреннюю ошибку — `500 {"detail": "internal error"}`.  
**Связи:** [T-10](threat-model.md#t-10) → [D-01](design-decisions.md#d-01). **Статус:** реализовано, тесты `tests/test_auth_api.py`, `tests/test_input.py`, `tests/test_security.py`.

<a id="sr-04"></a>
### SR-04. Неуспешный вход не раскрывает существование логина

**Требование.** Неверный пароль и неизвестный логин дают одинаковый ответ; для неизвестного логина сервер всё равно выполняет проверку хеша, чтобы не отличаться по времени.  
**Защитное свойство.** Нельзя составить список действующих логинов для целевого перебора.  
**Критерий приёмки.** Вход с неверным паролем существующего пользователя и вход с несуществующим логином → оба `401` с одинаковым телом `{"detail": "invalid credentials"}`.  
**Связи:** [T-02](threat-model.md#t-02). **Статус:** реализовано, тест `tests/test_auth_api.py`. Ограничение частоты попыток входа — запланировано, пока не реализовано.

<a id="sr-05"></a>
### SR-05. Доступ к ученику и связанным объектам — только в своей области

**Требование.** Администратор видит всех учеников. Преподаватель — только учеников с `tutor_id` = он, родитель — только с `parent_id` = он. Это правило действует для карточки, денежной истории, занятий, создания занятия и отчёта. Чужой и несуществующий объект неразличимы.  
**Защитное свойство.** Конфиденциальность денег и данных чужого ученика; невозможность изменить чужой баланс.  
**Критерий приёмки.** Преподаватель A запрашивает карточку ученика преподавателя B, создаёт ему занятие или отчитывается по занятию B → `404`, состояние БД не меняется. Родитель A запрашивает карточку или историю ребёнка родителя B → `404`. Запрос несуществующего id → тот же `404`.  
**Связи:** [T-03](threat-model.md#t-03) → [D-02](design-decisions.md#d-02). **Статус:** реализовано, тесты `tests/test_access.py`, `tests/test_lessons.py`.

<a id="sr-06"></a>
### SR-06. Преподаватель не получает контакты родителя и денежные данные

**Требование.** Ответы API для роли «преподаватель» содержат только поля, необходимые для ведения занятий: id, имя и класс ученика, сведения о занятиях. Телефон родителя, цена часа, баланс, оплаты и денежная история ему недоступны ни в одном ответе.  
**Защитное свойство.** Конфиденциальность персональных данных родителя и коммерческих данных школы от частично доверенного пользователя.  
**Критерий приёмки.** `GET /students` и `GET /students/{id}` от преподавателя → объекты ровно с полями `id`, `full_name`, `grade`. `GET /students/{id}/ledger` и `POST /students/{id}/payments` от преподавателя → `403`.  
**Связи:** [T-04](threat-model.md#t-04) → [D-02](design-decisions.md#d-02). **Статус:** реализовано, тесты `tests/test_access.py`.

<a id="sr-07"></a>
### SR-07. Занятие списывается с баланса не более одного раза

**Требование.** При любом числе, порядке и одновременности запросов на отчёт по одному занятию в денежном журнале появляется не более одной записи списания за это занятие. Записи журнала не изменяются и не удаляются.  
**Защитное свойство.** Целостность баланса: деньги родителя не списываются дважды.  
**Критерий приёмки.** Пять одновременных запросов отчёта по одному занятию → ровно один `200` и четыре `409`; в `ledger_entries` одна запись с этим `lesson_id`; баланс уменьшен один раз. Повторный отчёт после успешного → `409`. Попытка `UPDATE`/`DELETE` записи журнала в БД отклоняется.  
**Связи:** [T-05](threat-model.md#t-05) → [D-03](design-decisions.md#d-03). **Статус:** реализовано, тесты `tests/test_lessons.py`.

<a id="sr-08"></a>
### SR-08. Отчитаться может только преподаватель занятия и только о начавшемся занятии

**Требование.** Отчёт принимается только от преподавателя, за которым закреплено занятие и ученик, только если время начала занятия наступило. Статус «уважительный пропуск» не списывает деньги. Сервер фиксирует автора и время отчёта; после отчёта преподаватель его не меняет.  
**Защитное свойство.** Списания соответствуют реальным занятиям; у каждого списания есть ответственный автор.  
**Критерий приёмки.** Отчёт о занятии, начинающемся через 24 ч → `422`, баланс не меняется. Отчёт от администратора или родителя → `403`. После отчёта у занятия заполнены `reported_by` и `reported_at`; уважительный пропуск → `charged = 0`.  
**Связи:** [T-06](threat-model.md#t-06) → [D-03](design-decisions.md#d-03). **Статус:** реализовано, тесты `tests/test_lessons.py`.

<a id="sr-09"></a>
### SR-09. Уведомление о платеже принимается только от банка

**Требование.** Зачисление по уведомлению банка выполняется, только если подпись уведомления, вычисленная по секрету, известному банку и серверу, совпадает, а отметка времени уведомления не старше 5 минут. Иначе ответ `401` и никаких изменений.  
**Защитное свойство.** Подлинность источника денежного события.  
**Критерий приёмки.** Уведомление без подписи, с подписью другим ключом, с изменённой после подписи суммой или с отметкой времени старше 5 минут → `401`, баланс и журнал не меняются; корректно подписанное свежее уведомление → `200` и одна запись `payment`.  
**Связи:** [T-07](threat-model.md#t-07) → [D-04](design-decisions.md#d-04). **Статус:** спроектировано, не реализовано.

<a id="sr-10"></a>
### SR-10. Одна банковская операция зачисляется один раз

**Требование.** Повторное получение той же операции банка (по номеру операции) — повтор доставки, повтор ручного ввода или переигрывание — не создаёт второго зачисления. Тот же номер с другой суммой или для другого ученика отклоняется.  
**Защитное свойство.** Целостность баланса при штатных повторах доставки.  
**Критерий приёмки.** Повторное зачисление с тем же `external_id` и той же суммой → ответ с `duplicate: true`, баланс прежний; с тем же `external_id` и другой суммой → `409`.  
**Связи:** [T-08](threat-model.md#t-08) → [D-04](design-decisions.md#d-04). **Статус:** реализовано для ручного зачисления (`tests/test_access.py`); для уведомлений банка — в составе D-04.

<a id="sr-11"></a>
### SR-11. Тело запроса разбирается однозначно и в заданных пределах

**Требование.** Сервер принимает только `application/json` размером до 16 КБ в корректном UTF-8, ровно один JSON-объект без повторных ключей, без лишних полей и без неявного приведения типов. Денежные поля — целые в заданных диапазонах.  
**Защитное свойство.** Сервер и клиент одинаково понимают запрос; нельзя протащить скрытое поле или отрицательную сумму.  
**Критерий приёмки.** Тело с повторным ключом, NaN, двумя JSON-значениями или не-UTF-8 → `400`; с лишним полем, неверным регистром ключа, строкой вместо числа → `422`; тело больше 16 КБ → `413`; не JSON → `415`. Во всех случаях состояние не меняется.  
**Связи:** [T-09](threat-model.md#t-09); механизм — `app/input.py`. **Статус:** реализовано, тесты `tests/test_input.py`.
