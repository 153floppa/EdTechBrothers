## D-01. Серверные сессии с непрозрачным случайным токеном

**Контекст.** Субъект любого действия определяется по токену ([T-01](threat-model.md#t-01)). Требуется немедленный отзыв при выходе и при деактивации сотрудника ([SR-02](requirements.md#sr-02)): в школе преподаватели меняются часто, и уволенный преподаватель не должен сохранять доступ к ученикам до истечения токена. Утечка БД не должна давать действующих токенов и паролей ([SR-03](requirements.md#sr-03)).

**Решение.**
- При входе сервер создаёт токен — 32 байта из `secrets` (криптографический ГСЧ), возвращает его клиенту один раз и сохраняет в `sessions` только `SHA-256(token)` со сроком `expires_at = now() + 12 ч`.
- На каждый защищённый запрос `current_user` (`app/auth.py`) ищет сессию по хешу с условиями «не отозвана, не истекла, пользователь активен» — одним SQL-запросом. Роль берётся из `users`, а не из запроса.
- Logout ставит `revoked_at`; деактивация пользователя (`is_active = false`) отключает все его сессии без отдельной операции.
- Пароли — argon2id (`argon2-cffi`); для неизвестного логина выполняется проверка «пустого» хеша ([SR-04](requirements.md#sr-04)).
- Администратор создаётся только командой на сервере (`python -m app.cli create-admin`), пароль — из окружения или скрытого ввода.

**Обоснование.** Рассматривался JWT, подписанный сервером. Он не требует обращения к БД при проверке, но отзыв при logout и увольнении всё равно требует общего списка отозванных токенов, то есть того же обращения к хранилищу, плюс управление ключом подписи. Для одного приложения с одной БД случайный токен с серверной записью проще и сразу даёт мгновенный отзыв. SHA-256 без соли достаточен для токена: в отличие от пароля, у него 256 бит энтропии, и перебор по хешу бесполезен; медленный хеш здесь только замедлил бы каждый запрос.

**Связанные угрозы:** [T-01](threat-model.md#t-01), [T-02](threat-model.md#t-02), [T-10](threat-model.md#t-10).  
**Связанные требования:** [SR-01](requirements.md#sr-01), [SR-02](requirements.md#sr-02), [SR-03](requirements.md#sr-03), [SR-04](requirements.md#sr-04).

**Будущая проверка** (часть уже автоматизирована в `tests/test_auth_api.py`):
- **Условие:** тестовая БД, пользователь-преподаватель, выданный токен.
- **Действие:** (1) logout и повтор `/me` тем же токеном; (2) `expires_at` в прошлое; (3) `is_active = false`; (4) произвольная строка как токен; (5) поиск выданного токена в дампе таблиц `sessions` и `users`.
- **Ожидаемый результат:** (1)–(4) → `401`; (5) токен и пароль не найдены. Критерии — [SR-01](requirements.md#sr-01), [SR-02](requirements.md#sr-02).
- **Ещё не проверено:** поведение при недоступной БД (ожидается `500` без данных, а не пропуск проверки) и отсутствие токена в журналах прокси.

**Ограничения и последствия.**
- Каждый защищённый запрос делает чтение из БД: при недоступности БД API недоступен целиком (это осознанный выбор «отказ закрыт»).
- Токен действует до 12 ч без продления; украденный токен до logout владельца работает. Привязки к устройству нет.
- Таблица `sessions` растёт; удаление истёкших записей пока не реализовано.
- Без HTTPS-прокси (допущение модели) токен можно перехватить в сети.

## D-02. Область видимости в SQL и отдельная модель ответа для каждой роли

**Контекст.** Идентификаторы учеников и занятий попадают к клиенту, и их можно подставить ([T-03](threat-model.md#t-03)). Преподаватель — легальный пользователь с мотивом получить контакты семьи ([T-04](threat-model.md#t-04)). Нужно, чтобы ни один endpoint не мог «забыть» проверку и чтобы новое поле в таблице не утекло преподавателю автоматически.

**Решение.**
1. **Фильтр в запросе, а не проверка после загрузки.** `app/access.py` строит условие области видимости: администратор — все, преподаватель — `students.tutor_id = :user`, родитель — `students.parent_id = :user`. Это условие входит в `WHERE` каждого запроса к ученику, его журналу и занятиям (`get_student_in_scope`, `list_students`, `list_lessons`). Отчёт о занятии дополнительно требует `lessons.tutor_id = :user` и `students.tutor_id = :user` в том же `UPDATE`. Чужой объект не загружается, ответ — `404`, как для несуществующего.
2. **Белый список полей по роли.** В `app/students.py` три модели ответа: `AdminStudentOut`, `ParentStudentOut`, `TutorStudentOut` (только `id`, `full_name`, `grade`). Ответ собирается копированием только полей выбранной модели (`project`). Модели запрещают лишние поля.
3. **Роль разрешает вид действия, область — объект.** `require_role` закрывает действия, недоступные роли целиком (журнал и оплаты — не для преподавателя, отчёт — только преподаватель), и даёт `403`. Доступ к конкретному объекту решает область видимости и даёт `404`.

**Обоснование.**
- Проверка «загрузить объект, затем сравнить владельца» зависит от того, что разработчик не забудет её в каждом обработчике; при фильтре в SQL чужая строка просто не возвращается. Политика в одной функции `student_scope` проверяется тестами один раз для всех endpoint.
- `404` вместо `403` для чужого объекта не подтверждает, что ученик с таким id существует.
- Исключение полей по чёрному списку («убрать телефон») ломается при добавлении нового поля в таблицу: оно сразу уйдёт всем. Белый список требует явно решить, кому новое поле видно.

**Связанные угрозы:** [T-03](threat-model.md#t-03), [T-04](threat-model.md#t-04).  
**Связанные требования:** [SR-05](requirements.md#sr-05), [SR-06](requirements.md#sr-06).

**Будущая проверка** (часть уже автоматизирована в `tests/test_access.py`, `tests/test_lessons.py`):
- **Условие:** два преподавателя A и B, два родителя A и B, по ученику у каждой пары, у ученика A есть баланс и занятие.
- **Действие:** от каждой роли перебрать все endpoint с id чужого ученика или занятия и с несуществующим id; сравнить набор ключей в ответах преподавателю с `{id, full_name, grade}`; после каждой отклонённой операции сравнить снимок `ledger_entries` и `lessons`.
- **Ожидаемый результат:** все чужие и несуществующие id → `404`, запрещённые роли → `403`, состояние БД неизменно, ключей сверх белого списка нет — по критериям [SR-05](requirements.md#sr-05), [SR-06](requirements.md#sr-06).
- **Дополнительно запланировано:** тест-перечисление всех маршрутов приложения, который падает, если новый маршрут с `{student_id}` или `{lesson_id}` не покрыт проверкой области видимости.

**Ограничения и последствия.**
- При смене преподавателя у ученика старый преподаватель сразу теряет доступ, в том числе к отчёту по своим прошедшим, но не отчитанным занятиям; такие занятия должен закрыть администратор (пока не реализовано).
- Механизм не защищает от утечки через сам интерфейс за пределами API (скриншоты, переписка), а только от выдачи данных сервером.
- Фрагменты SQL с условием собираются из констант в коде; значения передаются только параметрами. Добавление нового условия с данными пользователя через f-строку нарушило бы решение — это проверяется ревью.

## D-03. Денежный журнал только на добавление и атомарный отчёт о занятии

**Контекст.** Отчёт о занятии меняет деньги родителя. Повтор запроса или два одновременных запроса не должны списать дважды ([T-05](threat-model.md#t-05)). Списание должно соответствовать своему начавшемуся занятию и иметь автора ([T-06](threat-model.md#t-06)).

**Решение.**
1. **Баланс не хранится, а вычисляется** как сумма `ledger_entries.amount` ученика. Оплата — запись `payment` (+), занятие — `lesson_charge` (−). Ограничения таблицы фиксируют знак и обязательные поля для каждого вида записи.
2. **Журнал только на добавление:** триггер `ledger_no_update_delete` отклоняет `UPDATE` и `DELETE`. Ошибка исправляется только новой встречной записью.
3. **Отчёт — один условный `UPDATE`** (`app/lessons.py`): строка занятия меняется, только если `status = 'planned'`, занятие и ученик закреплены за этим преподавателем и `starts_at <= now()`. В том же `UPDATE` фиксируются `reported_by`, `reported_at` и `price_snapshot` по текущей цене. Если строка изменилась — в той же транзакции добавляется списание; если нет — сервер определяет причину (`404` / `409` / `422`) и ничего не меняет.
4. **Второй барьер:** уникальный индекс `ledger_entries.lesson_id` — даже при ошибке в коде второе списание за занятие не будет сохранено.

**Обоснование.** Вариант «прочитать статус, проверить в Python, затем обновить» уязвим к гонке: оба запроса читают `planned`. Условный `UPDATE` в PostgreSQL при уровне `READ COMMITTED` блокирует строку: второй запрос ждёт первый, затем перепроверяет условие на новой версии строки и не находит её. Это не требует явных блокировок и ключей идемпотентности от клиента. Хранимый баланс-счётчик пришлось бы синхронизировать с историей; при журнале расхождение невозможно, а родитель видит, из чего сложился остаток.

**Связанные угрозы:** [T-05](threat-model.md#t-05), [T-06](threat-model.md#t-06).  
**Связанные требования:** [SR-07](requirements.md#sr-07), [SR-08](requirements.md#sr-08).

**Будущая проверка** (часть уже автоматизирована в `tests/test_lessons.py`):
- **Условие:** ученик с балансом 5000 ₽ и ценой 2000 ₽/ч, начавшееся занятие 60 мин.
- **Действие:** пять потоков одновременно отправляют отчёт `done` (общий барьер перед отправкой); отдельно — отчёт о занятии в будущем, отчёт после успешного, `UPDATE` записи журнала напрямую в БД.
- **Ожидаемый результат:** ровно один `200`, остальные `409`; одна запись с этим `lesson_id`; баланс 3000 ₽; будущее занятие → `422`; изменение журнала в БД → ошибка — по критериям [SR-07](requirements.md#sr-07), [SR-08](requirements.md#sr-08).
- **Ещё не проверено:** поведение при уровне изоляции `REPEATABLE READ` (второй запрос получит ошибку сериализации, а не `409`) — нужно зафиксировать уровень изоляции в настройках пула.

**Ограничения и последствия.**
- Сервер не может проверить, что занятие действительно прошло: ложное «проведено» о прошедшем занятии остаётся возможным. Защита — автор и время отчёта плюс видимость каждого списания родителю ([сценарий 3](../PROJECT.md#сценарий-3-контроль-баланса-родителем)).
- Исправить ошибочный отчёт может только администратор встречной записью; эта операция ещё не реализована.
- Баланс вычисляется суммой по журналу на каждый запрос; при тысячах записей на ученика понадобится снимок остатка, сохраняющий свойства журнала.

## D-04. Приём уведомлений банка: подпись HMAC, окно свежести и номер операции как ключ

**Статус:** спроектировано, не реализовано. Сейчас администратор вносит оплату вручную; часть решения — уникальность `external_id` — уже действует для ручного ввода.

**Контекст.** Ручной ввод оплат медленный и сам источник ошибок, поэтому планируется endpoint `POST /webhooks/bank`, на который банк присылает входящие платежи. Он открыт в интернет ([TB-2](threat-model.md#границы-доверия)), и поддельный запрос сразу превращается в деньги на балансе ([T-07](threat-model.md#t-07)). Банк штатно повторяет доставку ([T-08](threat-model.md#t-08)).

**Решение.**
1. Банк и сервер разделяют секрет `BANK_WEBHOOK_SECRET` (из окружения). Банк передаёт заголовки `X-Timestamp` и `X-Signature = HMAC-SHA256(secret, timestamp + "." + сырое тело)`.
2. Сервер вычисляет HMAC по **сырым байтам** тела до разбора JSON, сравнивает через `hmac.compare_digest`, проверяет `|now − timestamp| ≤ 5 мин`. Любое несовпадение → `401` без обращения к журналу.
3. После проверки подписи тело разбирается строго ([SR-11](requirements.md#sr-11)); плательщик сопоставляется с учеником по телефону; неизвестный плательщик не зачисляется, а попадает в список «непривязанных» для администратора.
4. Номер операции банка записывается в `ledger_entries.external_id` (уникальный индекс): повтор уведомления — `200` без новой записи ([SR-10](requirements.md#sr-10)).

**Обоснование.** Альтернатива — пускать на endpoint только IP-адреса банка. Это проще, но адреса банка меняются и задаются вне нашего контроля, а за общим прокси или облачным балансировщиком IP клиента может быть подменён заголовком. Подпись не зависит от сетевого пути и защищает от изменения суммы. Окно свежести ограничивает переигрывание перехваченного уведомления, а уникальный номер операции закрывает повтор внутри окна.

**Связанные угрозы:** [T-07](threat-model.md#t-07), [T-08](threat-model.md#t-08).  
**Связанные требования:** [SR-09](requirements.md#sr-09), [SR-10](requirements.md#sr-10).

**Будущая проверка:**
- **Условие:** тестовый секрет, ученик с привязанным телефоном плательщика, баланс 0.
- **Действие:** отправить на `/webhooks/bank` (1) корректно подписанное свежее уведомление; (2) его же повторно; (3) без подписи; (4) с подписью другим ключом; (5) с изменённой после подписи суммой; (6) с отметкой времени 6 минут назад.
- **Ожидаемый результат:** (1) `200`, одна запись `payment`; (2) `200`, записей по-прежнему одна; (3)–(6) `401`, журнал не изменился — по критериям [SR-09](requirements.md#sr-09), [SR-10](requirements.md#sr-10).

**Ограничения и последствия.**
- Компрометация секрета позволяет подделывать уведомления: нужна ротация (два действующих секрета на переходный период).
- Уникальность номера операции защищает от повтора **того же** уведомления. Если один платёж приходит двумя каналами с разными номерами (уведомление и последующая выписка банка), уникальный индекс его не распознает — это нужно учесть при подключении сверки с выпиской, прежде чем добавлять второй канал.
- Защита зависит от точного времени на сервере (NTP).
